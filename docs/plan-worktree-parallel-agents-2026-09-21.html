0 한 줄 결론

채택
작업마다 named branch worktree. Unity는 메인 폴더 1개만 연다. 에이전트는 다른 폴더에서 코드를 고치고, 끝난 것만 메인에 합친 뒤 Play로 확인한다.
보류
Cursor CLI + Orca ADE. 에이전트를 자주 2개 이상 터미널·폰으로 굴리게 된 다음에 깐다. 지금은 Cursor IDE /worktree로 같은 효과의 80%를 낸다.
하지 않음
git worktree add --detach로 병렬 작업을 오래 가져가지 않는다. 디태치는 Unity 브랜치 잠금 우회일 뿐이고, 커밋이 브랜치에 안 붙으면 유실된다.

“Unity를 보면서 작업 두 개를 동시에” = 모니터는 게임 하나, 뒤에서 코드가 둘. Editor 한 개가 폴더 두 개를 동시에 Play하지 않는다.

1 카톡 조언 판정

상대가 말한 것: GUI 대신 Cursor CLI, 원래 Orca ADE, Orca도 CLI를 깐다, 그게 더 효율, 헤드 디태치로 동시 2개 이상. 채팅에 「그건 좀 위험한데」도 있음.

말판정이유
Cursor CLI는 터미널 에이전트 맞음 공식 agent. 이 PC에는 아직 없음.
Orca ADE = 에이전트 전용 환경 맞음 onorca.dev. 서드파티. Cursor 공식 문서에는 없음.
Orca에서 Cursor 쓰려면 CLI 설치 맞음 Orca는 모델을 안 팜. 있는 Cursor 구독 + CLI를 묶음.
그 조합이 더 효율적 조건부 터미널 함대·폰 모니터링에는 맞음. Unity Play/검증은 안 빨라짐.
헤드 디태치가 동시 작업의 핵심 아님 핵심은 워크트리(폴더 분리) + 작업별 브랜치. 디태치는 우회.
디태치가 좀 위험하다 맞음 브랜치 없이 커밋 → 워크트리 삭제 시 유실. PR 가지가 없음.
이 컴퓨터 GUI로 작업하기 싫다 그 사람 취향 주인님은 Unity를 이 PC에서 Play해야 함. 동기 그대로 가져오면 안 됨.

3 워크트리 — 왜 / 어떻게

같은 .git을 공유하고 작업 폴더만 여러 개 둔다. 에이전트가 파일을 서로 안 덮고, Unity가 연 메인을 stash/브랜치 왕복으로 안 더럽힌다.

Git 제약

한 브랜치는 워크트리 하나에서만 checkout. Unity가 chore/assets-cleanup-unused를 잡고 있으면 에이전트가 그 브랜치를 다른 폴더에 또 열 수 없다.

방식명령쓸 때
정석 git worktree add -b feat/이름 경로 모든 실제 작업. PR 가능.
디태치 git worktree add --detach 경로 HEAD 잠깐 같은 커밋만 볼 때. 오래 금지.
Cursor 버그 주의
UI가 브랜치 없이 워크트리만 만들면 의도치 않은 디태치가 된다. 그건 정석이 아니라 사고. 오래 갈 작업은 반드시 git branch --show-current로 브랜치가 있는지 확인.

4 Unity 1개 + 작업 2개

하고 싶은 것Unity 1개
에이전트 B가 다른 폴더에서 스크립트 수정, Unity는 메인에서 Play됨
한 Editor가 두 폴더를 동시에 컴파일/Play안 됨
두 워크트리에서 동시에 PlayEditor 2개 = Library 2벌. 디스크·RAM 큼
같은 씬/프리팹을 두 에이전트가 동시 수정워크트리여도 머지 지옥
 
Unity          C:\Users\a3435\NeoSurvive        지금 브랜치, Play는 여기만
에이전트 A     ..\NeoSurvive-<task-a>           feat/task-a  (코드만)
에이전트 B     ..\NeoSurvive-<task-b>           feat/task-b  (코드만)
  1. Unity는 메인만 켠다.
  2. A/B는 각자 워크트리에서 고친다. 파일이 안 겹치는 작업만 동시에.
  3. 끝난 쪽만 메인에 합친다 (PR 또는 /apply-worktree).
  4. 그때 Unity에서 Play 확인.
  5. 다른 쪽도 합치고 다시 Play.

Unity MCP는 지금 열린 Editor 1개에 붙는다. 워크트리 B의 코드는 그 폴더를 열거나 메인에 합치기 전엔 Play에 안 나온다. Library 심볼릭 링크 공유는 락/DB 꼬임 위험으로 금지.
